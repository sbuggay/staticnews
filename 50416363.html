Before computers, there were computers. [1] It's obvious in hindsight, but all of these complex numerical calculations we take for granted were often not done by the same people applying them in various ways. I wrote a software to do it. It's not that difficult to make something like this now, it's just a Tauri2 app that has a kanban, priorities, history of everything the agent does. https://github.com/oscscull/quarterdeck

I don't think necessarily I'd recommend using or forking it (though go ahead if you like) but rather building something like it. It doesn't take that long.

The model I use is similar to yours, but revolves around the concept of "your turn". So you have a task or something, if the ai can work on it it's their turn. This creates a log of their actions and writes code. Then when it's time to e.g. review the draft code, it's your turn. That way, you can keep 5 things in progress, and just alternate turns, and you keep a history so you know what the context is. Then you apply this same model to other people, so reviewers, pr's that came to you. That's on "their turn". Your turn, ai turn, other people's turn.

For me, the most important thing is reducing the need to keep a mental map of all the work, software is cheap now so move the map (however you organise it) into a software (of your own creation). The problems you need to solve are how to retain context on the tickets so you can make judgement calls, and have the system prompt you in return, more like a human would, rather than a one way flow of requests. It's helped me with the burnout a lot.

3. Model creates a gitlab issue and presents it.

4. Model starts a grilling session. That is: it will keep asking me questions until everything for the task is addressed: design decisions, unclear elements, default behaviors, edge cases, conflicts with current behavior. Usually around 5-30 questions.

5. Loop of me answering and it asking a new batch of questions

6. Model updates the issue with all the decisions that were made.

7. Model with start implementing once I give the go. Once done it runs tests/validation and sends me a MR to review. (That takes anywhere from 5 mins to 2h depending on the task complexity, but on larger projects just the final test/validation/no regression step can be 10 mins)

8. I review / merge

The grilling is nice because for the most part if solves a lot of future issues by not allowing the model to make decisions you didn’t agree with, and it front-loads all questions so it can work uninterrupted. Very rarely does it need to ask a question during implementation.

But yeah most of my time is helping the agent define all the boundaries of the problem, decide how to break goals into issues (such as high level PM issues into technical issues) and so on.

Also one chat per issue which limits chat compaction.
