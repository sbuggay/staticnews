This is a very poorly conceived API. If developers' use cases don't fit cleanly into Apple's (narrow) idea about how a hypothetical app should work, developers will continue to feel like they need to request these expansive permissions. A good filesystem permission API could include any of these which would make users WAY safer and enable developers to request far smaller scopes:

- Allow the developer to specify the common location(s) that they need access to. Rather than having to have the user select the folder they want to grant access to, have the developer say "this app uses data in these 5 folders, do you want to grant that access" - so much clearer, and useful in cases where an app has to integrate with other apps through the filesystem. - Readonly access. Allow an app to read your files but prevent writes or deletes. - Time limited access. Allow some kind of access and allow the user to auto-expire it rather than having to remember it exists. - Allow for negative access (i.e. allow labels or tags on directories to mark them as sensitive and prevent access by default - browsers could do this for their cookie stores, `~/.ssh` could ship with it as a default, etc.)

Apple could have used this opportunity to think through the question of "why do developers ask for filesystem access, and how can we allow legitimate usage through well scoped access controls", but instead they built a bad API that will (I would guess) not actually allow developers to be more judicious or achieve any of the user-safety benefits.

Apple needs to learn to talk to (and listen to) developers.

Developers are important, but Apple understands that it must ultimately prioritise non-technical end users as their highest priority. Apple's approach puts control in users' hands rather than allowing developers to define the scope of access. Moving from Full Disk Access to user-selected folders is a significant security improvement, even if the API doesn't accommodate every developer use case.

It's also critical to recognise that data exfiltration is just as serious a risk as data manipulation. Read-only access doesn't prevent data theft, and time-limited access can't undo it.

comex|parent|prev|next|

Apple tried the first thing first. That was App Sandbox, and you can grant access to specific folders through the open dialog (or better yet, use the open/save dialog to access individual files so that no broad permissions are needed at all). But nobody adopted App Sandbox unless forced to.

Negative access is what came next, applied to all apps. By default, an unsandboxed program can access everything except specific protected directories, and can request access to those directories too, e.g. Documents, Desktop, Photos, other apps' data.

Full Disk Access is the last resort that turns all of that off. Or, well, was.

It's also the only way to access Messages, which might be why certain AI apps request it.
