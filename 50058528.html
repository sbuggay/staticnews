My favorite trivia is that busybox has built-in cgi-bin support (and `rclone serve webdav` seems remiss to not mention as well). `https://elixir.bootlin.com/busybox/1.37.0/source/networking/...`

Everything the post mentions is 100% true and well-reasoned, especially with the inclusion of pledge/chroot/etc. for dropping privileges.

There's two diametrically opposed deployment mechanisms:

1) stack towers of glop on top of each other until you're running a simple `echo "hello world"` on top of a docker container inside a vm in a proxmox server as part of a k8s cluster under a hypervisor running on remote compute...

2) just run `bash -c 'echo "hello world"'` and front it with CGI (stateless, single binary, yada yada yada...)

Take a peek at https://github.com/Domain/bash.cgi ... not that i'm suggesting that 'bash over busybox using cgi-bin' is the "proper architecture", it's more trying to illustrate that the amount of code that holds you back from being nearly truly "frameworkless" is tiny and easy to reason about.

For some of the internal tooling I'm doing for work, I've been tending towards:

    some-cmd [--json|--markdown] ...yet-more-args...
When you use the process and shell environment itself as a repl, you start trending towards `[--cgi-bin]` would "just" be another output type, and the ability (nay: foresight!) to ensure that your commands are independent, reproducible, and only depend on their input arguments leads you directly towards being runnable in both "hostile" (ie: firecracker vm / lambda-style) or very "comfortable" environments (ie: shell, debuggers, unit/integration tests).

MomsAVoxell|root|parent|next|

All the basics are there (chunked mode), I think you’d only need to do some thing things:

    local SSEHandler = class("SSEHandler", turbo.web.RequestHandler)

    function SSEHandler:get()
        self:set_async(true)
        self:set_header("Content-Type", "text/event-stream")
        self:set_header("Cache-Control", "no-cache")
        self:set_chunked_write()

        -- first event
        self:write("data: hello\n\n")
        self:flush()

        -- later events via IOLoop
        local ioloop = turbo.ioloop.instance()
        local count = 0
        local timer
        timer = ioloop:add_timeout(1000, function()
            count = count + 1
            self:write(string.format("data: tick %d\n\n", count))
            self:flush()
            if count < 10 then
                timer = ioloop:add_timeout(1000, timer)  -- reschedule
            else
               self:finish()
            end
        end)
    end

The Rust ecosystem isn't structured for the high friction dependency model the C has. Its structured around nearly frictionless dependencies so its no surprise that dependency trees are very large and frequently changing.

The typical C project has far fewer dependencies than the typical Rust project. Its less trouble to setup static analysis, address sanitizer, and similar tools for a C project than it would be to manage local copies of thousands of dependencies for a Rust project.

Also as manual programmers we're accustomed to programming being a team sport where you fit in gracefully into the ecosystem and build things with the maintainer and rest of the team in mind, but in the AI world, you can ignore the ecosystem, there is no maintainer (because you throw it away and have the AI write something else when the requirements change), and the rest of the team has all been laid off.

This is one of those cases. Many of the rules of thumb of professional programming no longer hold under the radically different economics of AI-driven development.
