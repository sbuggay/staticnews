Xylakant|root|parent|next|

The comparison between golang and rust comes up a lot. Golang is certainly a capable language, but I think it's not filling the same niche that rust fills.

While golang often is comparable to rust in a lot of scenarios, there's also quite a bit of a difference between the two to make this a non-religious choice based on technical merits and needs. For starters, golang comes with a runtime and a gc. This is an absolutely fine choice in a lot of places, notably when you start writing web/desktop components from scratch. It does, however, make it impossible to use in some places where rust is usable: Very small memory/cpu constrained devices, places where you need predictable (not necessarily fastest) performance, control over allocation/deallocation and most notably, places where you want to replace one component written in C/C++ with something memory-safe. Golang brings a runtime and as such you can't just embed go code into a C binary. With rust you can, it's one of the explicit design goals of the language and drives a lot of the design choices that went into it (for example the no GC approach to memory management)

This also explains why it's interesting to mention the language: Rust caters to a specific set of programming language needs. If I have a need for the things that rust provides, then go isn't going to be a replacement. If I want a voip stack that I can integrate into a C application because I happen to have one, then I either need C, C++ or Rust (or anything else that compiles down to a plain object file)
