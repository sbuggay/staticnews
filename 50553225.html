Yesterday night, i reverse engineered the cloud connection plugin to my cctv camera in about 2 hours with Gemini.

Started off with me searching for what Chinese OEM made the product. Then tried out existing GitHub projects to see if it works but they were failing.

Spent 15 minutes to write a script that started their desktop software on a different network namespace and ran tcpdump in it. Captured exactly only the things i needed without any noise. Turned out it was using a different server url and credentials than the GitHub projects. Opened Ghidra to inspect the dlls that matched the strings i was looking for.

After that, I got lazy and handed over the task to Gemini to find the username and key they use to authenticate with the servers. It took about 30 minutes or an hour. A lot of it was me changing models because the llm servers were busy. It simply wrote a little script that ran through various strings it fetched from the binary to see if it can generate the authentication credentials.

Now my Home Assistant will be detecting if my car is parked in the parking lot or not. Life is good.

> This is variation of scientific method and it significantly helps agents when they are getting stuck on some problem. Stops it going in circles. By forcing it to do definitive experiments. No endless guessing and trying random things.

These "guessing loops" are my main annoyance when REing with Claude (mostly Opus 4.8, due to the restrictions on newer models). On harder/larger targets, I have to constantly babysit it and tell it to "stop guessing".

For truly black-box reverse engineering, yes, hypothesis-testing is the way to go (it's all you can do). But in most cases all the information is available to arrive at an answer deterministically, it just needs to be worked through meticulously. As an experienced human I have strong intuitions and I can work much faster under a "guess and check" model, but I prefer to use Claude as an "unstoppable RE juggernaut" with superhuman patience and determination, tracing method invocations all the way from A to distant subsystem B (for example).

Another big win for hardware RE is from tasking the LLM with writing unicorn emulation harnesses, e.g. for bootroms and firmwares. It's pretty good at the classic "figure out which MMIO needs to be stubbed/simulated next to progress the boot" loop, although sometimes it tries to take egregious purpose-defeating shortcuts.

georgemcbay|parent|next|

> I guess Android apps are just easy to reverse engineer or something.

Android apps are indeed easier than average to reverse engineer as they are effectively Dalvik (JVM-like) bytecode wrapped in a zip file format, and Dalvik/JVM style bytecode is among the easiest compiled/shipped executable formats to decompile to a usable source code representation.

More often than not the only protection they have is symbol/function name obfuscation, which makes things a bit tedious for human reverse engineering but which doesn't slow LLMs down much.

(and if you need, before the /clear, just have it save all its memory as an .md file you can use as input to the new session).
