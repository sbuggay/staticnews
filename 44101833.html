Here's o3's speculation on what Claude's transaction machine might be:

*1 · Self-assembling transactional runtime* Every edit is logged as an atomic, idempotent event in an append-only ledger. Replaying the log materializes the codebase, enabling instant time-travel, rollbacks, and hot-swap execution. Source control, build, and runtime collapse into one continuously replayed “transaction stream.”

*2 · Semantic-transaction compiler* Instead of tokens, you author high-level intent blocks like `AddLoginScreen ⇒ Route("/login") + Component(LoginForm)`. The planner resolves dependencies and constraints, then emits concrete code, migrations, and tests. Coding becomes declarative composition of intent transactions.

*3 · Micro-economic coding market* Each keystroke is a micro-transaction bidding for runtime fitness (correctness, speed, maintainability). An automated cost model rewards profitable lines and taxes or prunes wasteful ones. The “machine” evolves the codebase by market selection rather than manual refactor passes.

simonw|parent|prev|next|

My best guess is that this is a reflection of how these things actually work.

When you "chat" with an LLM you are actually still participating in a "next token" prediction sequence.

The trick to get it to behave like it is a chat is to arrange that sequence as a screenplay:

  User: five facts about squirrels

  Assistant: (provide five facts)

  User: two more

  Assistant:
When you think about the problem like that, it makes sense that the LLM is instructed in terms of how that assistant should behave, kind of like screen directions.
