I'll try this.

The way I have to resume downloads in Firefox is

1. Move the .part file to a temp file

2. Start the download again; a new .part file gets created

3. Pause the download

4. Move the temp file to the .part file, overwriting it

5. Unpause the download; it resumes from where the old .part file stopped

This is only necessary if a "one-time" download link gets interrupted part-way through, eg. by a flaky connection. Attempting to resume a one-time link like normal gets (I assume) a 400 response and FF kills the .part file.

edflsafoiewq|root|parent|next|

The situation AFAICT is something like this: the server mints unique download URLs which can only be used once. This is generally so they can't be shared. It serves the URL to the first comer and when that connection drops (maybe with some timeout) subsequent requests to that URL produce 410 Gone. So if your download fails halfway through, you can't re-request the same URL with a Range, which is how normal resumption works. You need to get a new one-time URL minted and download that.

So from the browser's perspective, these are two distinct, unrelated URLs. There isn't a mechanism where it can know they are backed by the same file.

This browser behavior seems pretty reasonable. I'd try fixing it by doing something different on the server.
