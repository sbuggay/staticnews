labcomputer|root|parent|next|

No, it's a more fundamental problem: Zip codes are not "areas" and have no boundary.

Instead, what they are, are collections of mail delivery points. The "full" 5+4 zip code represents one mail delivery route that a postman follows to deliver mail. And the "fuller" 5+4+2 zip code has the last two digits of the street number.

So couple issues with trying to make polygons from zip codes:

1. There is no guarantee that a given zip code has a finite area. There are several zip codes that exist at a single street address. So... is that a point? Is it the footprint of the building where the mail is delivered? Maybe a hexagon with some minimal side length? Examples: Several IRS return addresses, and some large hospitals.

2. There is no guarantee that a given zip code has a contiguous polygon representation. It depends on the algorithm you use to generate polygons from address points.

3. There is no guarantee that a given zip code has a fixed geospatial representation. Example: the armed forces zip codes for delivering mail to overseas personnel on deployment. The AFPO zips represent "wherever the troops happen to be today". How do you represent that as a polygon?

This is why the USPO has long resisted publishing polygons. It doesn't make sense at the conceptual level, so there are a bunch of weird edge cases you wouldn't expect if you naively treat them as polygons.

ALSO: The census does publish zip polygons. Some of those have zero people living in them (like the hospitals and IRS locations), so you can get weird div-by-0 effects if you aren't careful.

Another very common use-case for zip code polygons is "I have a zip code, just tell me where it is, damnit!" Maybe they want to estimate shipping distance without hitting the shipper's API.

Part of the problem here is that the AFPO zips do have a physical location for this purpose, which is the facility where mail and parcels are delivered from the USPS to the AFPO. And your users will probably expect you to know that's what they mean. So when you try to explain that "actually an aircraft carrier is constantly moving and we're not allowed to know where it is", they will think you are being pedantic and condescending, and look for someone else to sell them polygons.

But let's say the user actually wants to forecast sales of the new ThingyWidget 3000 by estimating the average weather by customer zip code (by getting the polygon for each zip and the doing a spatial join to weather data). When they do that for the AFPO drop-off point, they're going to get a completely wrong estimate of the weather because the people receiving mail at the AFPO zip are not physically present at that place. So when you explain that "actually that is the physical location of the AFPO facility" they will also think you are being pedantic and condescending, and look for someone else to sell them polygons.

Notice how you're damned if you do and damned if you don't?

Any choice you make for polygonalizing zip codes will be wrong for some use case, and it will be spectacularly wrong for certain edge cases in very intuitive ways that certain users deeply care about and will blame you for.

Which brings me back to the point: You can make a set of polygons for zips which is "good enough" for many use-cases, but ultimately you cannot represent zips as polygons in a way that is suitable for all use cases because, once again, zip codes are not polygons!

Reminds me of one of my favorite little rabbit holes, trying to find this data for Canada:

Canada is one of the only major countries where the postal/zip code boundary data is not available as an open data set. Canada Post has a monopoly on that dataset. As a Canadian GIS person it drives me nuts as many other Candian government GIS programs have been active in the open data/open-source world for decades. Even crazier is that Statistics Canada has an open database of all addresses in the country here https://www.statcan.gc.ca/en/lode/databases/oda that has a postal code column, but it's empty for all addresses.

Anyone who has tried to create their own dataset of polygons has usually ended up being chased down by Canada post. There is a company called Geocoder.ca who made a geocoder and when you passed in a street address with a postal code in it, it would keep track of that, and geocode based on the street address. Over time they built up a database of coordinates and postal codes and were able to generate their own approximate boundaries that where pretty accurate. Canada Post went after them: https://geocoder.ca/?sued=1 Their data is still free for non-profits, and relatively cheap for commercial purposes: https://geocoder.ca/?freedata=1 The only other open data related postal codes you will find easily available is Forward Sortation Code boundaries (FSA) which is the area that represents the first three characters of a Canadian Postal code. For example, postal code "N0R 1K0" would have an FSA of "N0R". For demo's and some analysis scenarios that can often be enough.
