lambda|parent|next|

The problem with this model is that then you try to build all of the libraries that you anticipate users are going to need in one big go before you release version 1 of you language. Because you're trying to do a lot at once, they don't ask get the proper attention they deserve. Then, because of stability guarantees, you're stuck only making backwards compatible changes in the future (or you risk either constant breaking changes, or big changes where a lot changes at once forking the ecosystem, like Python 2 to 3). So if you made any mistakes in the library, you're stuck with them, only being about to deprecate but never really remove them.

The alternative is to keep a relatively small standard library, and a good package manager, to make it easier for people to iterate on API design in third party packages. Major version changes in a single library can have much less impact accross the ecosystem than standard library packages. Eventually you may get a de facto standard, and sometimes they are then later incorporated into the standard library.

This model isn't without its downsides; it can sometimes mean fragmentation when standardization would help, sometimes these de facto standard libraries can become important enough that they run into the same ecosystem fragmentation issues on major releases. But it allows for more flexibility.

The latter model is what the Rust project decided on for everything outside of the most fundamental time types. Dates and times and timezones are notoriously hard to model in code, and easy to create API designs that are full of footguns, so this is a place where that extra freedom to iterate was more important than standardizing on an API early on.

That iteration has led to a number of different libraries, including time, chrono, and now jiff, allowing for exploring the space of API design to really get it right rather than being stuck with what was available early on.

kccqzy|prev|next|

The one thing I don’t like in most datetime libraries is that for timezone names they all just defer to IANA time zone database. This database is a wonderful compendium of all time zones historically in use, but it is absolutely programmer oriented and not user oriented. There are two main problems: (1) it’s based on large cities; (2) it captures history faithfully.

The first problem is the bigger problem. If you are writing an app that asks the user for a zoned time, the user will want something like Nov 16 7pm eastern time. But EST is of course highly ambiguous and so is EDT. (The database actually gives EST to Panama Time and leaves EDT undefined.) The correct solution is either EST5EDT or America/New_York. Neither is user friendly. The first string EST5EDT looks like gibberish to the average user. The second raises concerns in all other cities sharing the same timezone as New York. Why not have an entry for Philadelphia or Washington D.C.? Some even say it is inherently classist to pick the city with the biggest population, not the most important by some other metric. Is New York more deserving than our nation’s political capital? Why is Los Angeles more deserving than San Francisco, other than the fact that the maintainer of the database is physically in Los Angeles? This is an actual criticism in iOS calendar app on the now defunct Apple forums. If you want the user to pick a timezone you better make sure Eastern Time is an allowed option, and maybe also include all the cities and municipalities in the zone; that’s what the newest iOS does. But in any case almost every developer now hard codes a mapping from Eastern Time to America/New_York if their audience is U.S. This feels like duplicative work better done in a library. The fact that a new library reaches 1.0 and doesn’t plan to add this might mean a lack of ambition to tackle this problem.

The second problem is the fact that the timezone definitions change according to the actual rules in effect in history. This is sometimes not what you want. Indeed I notice that most if not all date libraries use the proleptic Gregorian calendar (our current calendar system extended backwards); no library that I know of automatically switches to Julian calendars before the cutoff. Why this inconsistency? I’d argue that when most humans express a zoned time they expect the current rules to be extended backwards. People forget the daylight saving rules change in the 2000s when talking about times before that change and expect the current rules.

Not to be a detractor here for this library given the hard work of burntsushi, but we should aim higher.


burntsushi|parent|next|

IANA time zone identifiers are baked into RFC 9557, which extends RFC 3339. For sure, IANA identifiers are generally for programmers.

> The second problem is the fact that the timezone definitions change according to the actual rules in effect in history. This is sometimes not what you want. Indeed I notice that sometimes all date libraries use the proleptic Gregorian calendar meaning our current calendar system extended backwards; no library that I know of automatically switches to Julian calendars before the cutoff. Why this inconsistency? I’d argue that when most humans express a zoned time they expect the current rules to be extended backwards. People forget the daylight saving rules change in the 2000s when talking about times before that change and expect the current rules.

Good question. One part of this answer is that the IANA tzdb does not only contain daylight saving time transitions. It also includes transitions from one offset to another, perhaps because daylight saving time was stopped or started. The other part of this answer is, I would guess, more pragmatic. Namely, we have structured data delineating time zone transitions back at least a century. If you go far enough back, then indeed, time zone transitions stop happening. We, however, do not, as far as I'm aware, have shared structured data delineating changes in calendar. This would also need to be organized by both location and time. For example, the Julian calendar was not dropped in favor of the Gregorian instantaneously everywhere. Some countries, like Russia, continued using the Julian calendar into the 20th century.
