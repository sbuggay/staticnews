I used to think GraphQL was a pretty good idea. You can change the shape of your model, do complex queries, and ultimately switch out the backends. What's not to love?

But over time I've come to realize that those features aren't all that helpful. More fixed and static responses are much easier to manage. They force the caller to do things in a performance oriented way for the backend. And, importantly, all telemetry is based on CRUD/REST style endpoints. You lose a lot of that if you just have a GraphQL endpoint. It makes it supremely hard to see how you are being called or what you can drop.

It's flexible, but it adds too much undo complexity to a system that adopts it.

Well thought out REST endpoints organically grown as usage is required or observed trumps hyper flexible endpoints created because "Who knows what the user might need". And particularly in the age of LLMs and AI where adding and deploying new endpoints can take hours rather than days. Or making/updating a client for a service is extremely fast, there's just no reason not to go down that route.

marcus_holmes|parent|next|

I fundamentally object to the idea that the schema you need for the database is the same schema that you need for the front end. This is ORM thinking, and ORMs are universally stupid.

The classic example is user passwords. For the database schema, it makes perfect sense to store the password hash alongside the user's other details. For the front end, it's positively dangerous to return the password hash when all the front end needs is the user name and avatar url.

I think part of the attraction of GraphQL was being able to specify that front-end schema properly, and let the front end create its own queries on that schema.

But then folks decided that the front-end schema should be generated from the back-end schema because maintaining two schemas was too hard.

And, of course, the majority of what I've seen GraphQL as actually used, there's one query, fired at page load, that returns a giant json blob with all the data in it, because the front-end devs don't want to deal with quering for what they actually need.


dofm|root|parent|next|

> I fundamentally object to the idea that the schema you need for the database is the same schema that you need for the front end.

Object all you like, but it is not inherent to the idea of schema-first GraphQL, is it?

The “schema” in “schema-first” is not the database schema. It is the schema definition language document.

“Schema-first” does, broadly but not universally, suggest a mapping between the schema definition and some scheme of business objects or structures that can be instantiated, but it does not at all insist they are database ORM objects.

It implies only that the code follows from the schema definition document, rather than the schema definition presented by the endpoint emerging from code.

See for example Golang’s gqlgen: https://gqlgen.com/

They can be lightweight business logic models that do or don’t have an ORM mapping, plus invoking ordinary methods identified by attribute decorators in the schema definition.

It’s still a very long way further down the line than writing complicated resolver functions and managing all the complex GraphQL context stuff.

> This is ORM thinking, and ORMs are universally stupid.
