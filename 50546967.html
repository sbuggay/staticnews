Cool article, thanks! Nitpick: the reason behind the little endianness _originally_ was data access speed-up on 2200, not arithmetic. The 2200 only had 8-bit arithmetic (as did 8008), but its address bus was processed low-to-high. The arithmetic angle became relevant in 8080, with its 16-bit arithmetic. Side benefit: casting between 8- and 16-bit data using the same address.

Another nitpick: the article says 8085 had multiplexed address/data bus. This is actually also true for 8008, 8080 before it, and 8086, 8088, and 80186/88 after it.

> why does a modern PC still wake up pretending to be a chip from 1978?

I don't know why Intel and AMD are still doing this.

If they changed their CPUs to start in long mode (or even just 32-bit protected mode), nobody would notice except BIOS writers.

And BIOS writers expect to have to change their code to support new CPUs anyway. If Intel and/or AMD made it an ultimatum, the BIOS vendors would comply.

I know Intel had a plan to remove real mode and 16-bit support entirely, X86S, which they abandoned. But a lot of people opposed that because it would have harmed backward compatibility, including the ability to run older OS versions under virtualisation. Changing the physical CPU to no longer start in real mode would be invisible to everything except the BIOS, and even for the BIOS, only its early initialisation code would have to change.

skissane|root|parent|prev|next|

Actually, I just learnt something...

Only the BIOS init code cares about which mode the BSP starts in

But the OS cares about what mode the APs start in. Most operating systems use INIT-SIPI-SIPI, which starts the APs in real mode.

If an OS uses ACPI 6.4 Multiprocessor Wakeup Mailbox instead, then UEFI does the INIT-SIPI-SIPI on the APs, puts them in 64-bit long mode, then hands that to the OS. However, few bare metal UEFI implementations actually implement it, it is mainly implemented by hypervisors to support confidential VMs.

So, Intel/AMD could make the BSP start in 32-bit protected mode, with minimal BIOS code changes; but the APs would still need to start in 16-bit real mode. They couldn't make the APs start in a different mode until they got everyone to move off INIT-SIPI-SIPI.

GeorgeTirebiter|parent|next|

The way the IBM 1401 does it, because it's a variable word-length machine (fields being delineated by Word Marks, which is a bit in each core location specifically for marking the end of a field / instruction).

So the number '123' is stored in sequential memory locations: x, x+1, x+2 with a word mark under the '1'.

To add (assembly: A X,Y) e.g. '456' to said number at y, y+1, y+2 (in this case the 4 need NOT have a word mark (but usually does) because a word mark in either field ends the operation) the machine starts at the high-order address -- so it starts at address x+2 and y+2, develops any carry, applies that to x+1 and y+1, adds, and finally moves to the hundreds digit, adding any carry from the tens. (The destination address holds the sum in this case, '456' goes to '579')

Also, to move '123' somewhere, you specify the address of the '3' and the field is moved right-to-left to the destination (decrementing the internal pointer, and stopping when finding a word mark).

So, it more or less was Big Endian, but was still able to use a serial ALU by starting at the highest address!

Yes, and it's also consistent with normal bit numbering: bit n has place value 2^n, while byte n has place value 256^n. The vast majority of BE processors actually have LE bit numbering.

The only exception is IBM, which used both BE bit and byte numbering. (Bit 0 is the most significant bit, and its value depends on the width of the data in question --- exposing the major disadvantage of BE, i.e. a length-dependent term.)

An old adage I've heard and found useful: "Little endian is Logical; Big endian is Backwards."
