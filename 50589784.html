> Next, we optimize graphics by sending a sort of "grid" of pixels. Each cell has its own updates, where the previous frame is compared to the current frame to catch and send updates, avoiding having to constantly stream the full screen.

mosh does this too, with the caveat that it's not transparent to terminal escapes. for instance, if you try to run some modernish "tui framework" remotely over mosh, things like clipboard access won't work at all, because mosh just cares about how the terminal should look.

there are workarounds to smuggle the OSC sequences in other places, so you can get all escape sequences through. I usually have a process tree that looks something like this

  Ghostty
  |- screen -e^Zz -S meta
     |- screen -e^Oo -S workspace1
     |  |- zsh
     |  |- zsh
     |- mosh somehost -- screen -e^Oo -S remotework1
     |- mosh otherhost -- herdr
and escape sequences work just fine from inside the nested local screen session, the screen-mosh-screen connected to somehost, and the screen-mosh-herdr on otherhost.

xxpor|prev|next|

For TUIs, I wish a 5250-style block based terminal had won over VT100 stream based terminals.

For those not familiar, with a block oriented terminal, the native "chunk" of data is an entire screen. So you can put information in there like "this is a text box". This allows, for example, you to move around the screen with tab and type _with no round trip back to the server_. There's 0 latency. Data is only sent when you hit enter.

On high latency or flaky connections the experience is a million times better.

There is no reason or advantage to delivering a gui via enhanced terminal graphics. It is not good engineering.

It's amusing, sure. But that's what it is, a silly thing that's fun to do just to see it done.

some terminals have some extra features that can be completely abused into rendering a gui, inefficiently, and unportably.

TTYs and vtxx terminals are so great because they are ubiquitous, but servers and clients that know kitty graphics are not.

Terminals are useful because they only use a tty, and all terminals since before they were even software or networked, all already support the same basic tty and terminal feature set. It's a standard that everything in the world already supports.

It's only useful as long as that's true. Once you do anything else, you are no longer within that standard and now you need a special server and a special client, and then you no longer have any advantage for doing it over ssh except that the firewall rules already allow the ssh port.
