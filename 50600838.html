> If I understand contracts right, as in, that they're a basic form of dependent typing,

No, C++ contracts have nothing to do with the type system. It is purely predicate calculus using Hoare logic where subsets of state space are filtered from a larger program state space. The program is basically "steered" through the global state space using pre/post conditions.

Note however that theoretically (i.e. following from Curry-Howard correspondence) contracts can be thought of as dynamic counterparts to dependent types. But that is in a functional language with typing using constructive logic and not in an imperative language.

btown|root|parent|next|

To expand on this, my understanding is: the thing that held back approval (from the national bodies, not the committee itself) was that build configurations could turn off contract checks, which run at runtime, and still be standards-compliant. They wanted library authors to be able to write checks that will actually run, regardless of the build configuration of the person compiling!

So the “fix” was to let the author mark individual contracts as always enforced at runtime, with pre<enforced>. That, in turn, means a library’s key safety checks (bounds, null, etc.) can’t be silently dropped in a “loose” build configuration, which pushes things down a safer path.

Clunky IMO, but rather reasonable as a response to Rust!

It brings things closer to a world where: if you use these “safe” libraries, your program will stop rather than run unsafely, no matter how it was built.

Maxatar|root|parent|next|

The issue is more specific, namely that in C++ most code uses header files, and contracts must be specified in the header file, so that it creates the possibility where the same function can be compiled with and without contracts on and off.

This is known as an ODR-violation, where the same function is compiled with two or more definitions, and there's no rule in C++ to pick which definition should be used. One way to resolve this would be to introduce a rule to pick between these definitions (always pick the function with the contract check disabled, or pick with it enabled), but no one could agree on which rule to use and even if they did it would not work for shared libraries.

There is no doubt that once contracts get standardized, compilers will offer a flag to disable them categorically, ie. disable all of them across all definitions. That won't be an issue because then all definitions will be consistent. But the original proposal allowed flipping contracts on or off per "source-file" with the hopes that developer discipline would ensure that people were consistent about its usage.

kmeisthax|root|parent|next|

The main things that C++ has that Rust doesn't is inheritance[0] and move constructors[1]. In practice you won't notice either unless you're writing bindings to C++ code or UI toolkits. More importantly, neither feature imperils memory safety. Rust left those out for reasons of taste[2].

What actually imperils memory safety in C++ is primarily cultural, not technical. In Rust, we have a lot of both stdlib and third-party library code that is properly designed and works well. Borrowck and the unsafe keyword are the primary technical enforcement of Rust's safety requirements, both of which could be grafted onto C++, but it probably would not do nearly as well of a job in C++ as it does in Rust.

Take, for example, the C++ contracts feature. The reason why the ISO vote on C++26 failed is because the ISO spec for contracts specifically allows compilers that do not enforce them. This is absolutely, obviously stupid; but it is also fairly typical of C++ culture. C++, being derived from C, is plagued with the notion that the programmer is ultimately responsible for performance, even though optimizing compilers have been a thing for decades and it is genuinely difficult to find performance improvements just by shuffling lines of code around. That's why they would consider it acceptable to add a safety feature and allow it to be turned off.

In Rust, you can't turn off the borrow checker. No, not even in unsafe code. Unsafe lets you lie a little to the borrow checker and type system - you can construct references from raw pointers or transmute types. But you are ultimately still beholden to those rules and you'd better make sure everything you do lines up right regardless of what happens in safe Rust.

[0] Rust traits can do inheritance-like things, so bindings to object systems with inheritance (such as GObject) will use them a lot. This still, however, results in a lot of boilerplate needing to be written - at the very least, every subclassable type needs its own trait for override implementation, etc.

[1] In Rust, all types are movable at any time. This makes self-referential structs impossible to implement safely, which means linked lists are a pain and async is basically impossible to do soundly. Pin<T> implements immovable types as a special kind of smart pointer, which is good enough to make async sound (albeit at the cost of a lot of compiler magic). But in C++ all types manage their own movement: this would be the equivalent of having a Move trait that gets called every time a struct gets moved.

[2] Specifically, "composition is preferred over inheritance." Inheritance requires developers invent a taxonomy of parent types and much early C++ code was plagued with nonsensical taxonomies.
