Shameless plug, but a bit related to jj:)

I recently created a project which utilizes FUSE to serve git files directly from object store without a checkout. Main motivation was to sepeedup a worktrees creation (I work on a huge monorepo). In my case it helps a lot - now I wait a second instead of a minute. But then I realised there are other interesting features which having vfs opened:

- tree structure of related branches (simplest case of that are stacked PRs) which rebases itself

- live preview of merge state or any node of such tree

- on demand creation of a new branch which merges any of the existing ones very cheaply (e.g for a throwaway build check)

- quick and simple comand which shows conflicting files between selected worktree and all others

- agents gets notified about such conflicts when they happen

I was able to design it in a way so git sees those virtual workspaces as normal worktrees, and all git commands works exactly as you would expect. So I think for some people, especially on the very big repositpries, it might solve a few problems they try to solve with jj.

https://github.com/pkukielka/gitfold

A few typical use cases: https://github.com/pkukielka/gitfold/blob/main/docs/guide.md

I have a good story around these features.

At the start of the day, I resumed working on a feature; there's no staging, so modifications I make are all stored as the current change.

Later that day I realised I needed to actually save the version of the feature that existed when I started work that morning.

So into the evolog I go (`jj evolog`). It's a record of all commits that a change has been; I could scroll back through the recorded changes, find the first change made that day, and then 'jj new' to create a change that represents that work.

It felt magical, to just be able to jump back to a project state that I didn't explicitly record, then save it.

JJ, using the squash workflow, is brilliant for working with Claude

The workflow is straightforward: I create a named revision for the work I want to do, then an unnamed revision on top. I prompt Claude, changes land in the unnamed revision, I review those, squash the parts that I'm ready to accept, prompt some more to iterate on the parts that aren't up to par yet. I instructed Claude that I use jj with the squash workflow, so it should never touch revisions with a non-empty description (I also needed to tell it to shut up about that check), and the whole thing flows pretty damn smoothly.
