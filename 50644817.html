This is the single most important attack vector for SAAS companies. It has been for a long time --- this is the standard fact pattern for every SAAS breach --- but much more so today. As the number of employees grow, the likelihood that one of their laptops will get compromised approaches 1. When that happens, the attacker will be able to push code to Github, and if that code gets deployed, you're owned.

In 1Password's case, the absolute worst-case catastrophe is mitigated by the fact that customers retain custody of their unlocking secrets; 1Password (at least in the normal product flows) simply doesn't hold it. But an attack like this implicates every catastrophe short of that worst case.

Change velocity in 2026 is unreal and that trend is going to continue. You could not outcompete 1Password by building a handcrafted artisanal password manager backend (witness all the commercially successful password managers that don't even share 1Password's customer secret custody model). You have to accept insane PR rates as a premise to do modern SAAS security.

So the question then becomes: what is review? It's not what r/programming assumes it is; you almost certainly can't literally have a team of people line-by-line reviewing PRs anymore, at least not across the whole codebase (you can and should probably do a threat model for your codebase and institute stuff like that on a case-by-case basis, though). What you can realistically expect to review for is change provenance; a human developer signoff of some sort. But it's tricky! The attacker owns your email during the window of attack.

I think this is a fun problem to noodle on, and someone could probably come up with something here that would make a real difference.

When I’ve daydreamed of writing my own 1p replacement (from reading this thread, I guess I’m not as unique as I believed), my solution has been to replace cloud storage with cloud discovery. Syncthing does this. If the server on the internet is stateless and only serves to connect two clients who then talk to each other using encryption based on pre-shared keys, you get sync with a much smaller attack surface. Even if the server is hacked, the clients are responsible for authenticating each other, so there’s not much damage a compromised discovery server can do other than make the sync process fail.

The trade-off is that sync only happens when both devices are online at the same time, so there’s no asynchronous replication. But between keeping my most sensitive data on a server somewhere, even if it’s encrypted, and forgoing asynchronous replication, the latter is far more preferable to me.

It mostly limits the data that is online and available to be hacked at any time. If a discovery server is hacked and starts trying to MitM the sync for later decryption, only the in-flight passwords would be compromised, not the entire vault. If a hack is detected, a simple date range between when the hack occurred and when it was detected and fixed could be used by clients to enumerate all affected passwords that need to be changed. Also, clients wouldn’t have to use the same discovery servers each time, making it harder for attackers to target any specific user. If a nation state (the most likely entity capable of decrypting a full vault blob) is targeting a dissident, they’d have to compromise all discovery servers the clients might use rather than just a single server holding the entire vault. If a vault is online in its entirety, even if it’s encrypted, the hack only needs to last seconds before it’s detected for the attacker to get everything.

TimTheTinker|root|parent|next|

I reviewed the 1Password white paper a few years ago, and came away with the impression that (a) it's far better than any of the other password manager papers I reviewed, especially since they use cryptographic primitives to guarantee vault security, and (b) the greatest security gap is the supply and delivery chain associated with client software.

That is, they are only ever as secure as the client software is (browser plugins, CLI, 1Password.app/exe, etc.) -- their dependencies and the servers that host them.

Yes, customer vault data is as secure as it could be: E2EE, double-encrypted at rest (filesystem encryption and 1P-encryption) and double-encrypted in motion (TLS and 1P-encryption), and a massive bounty for working exploits. The client software that decrypts it is only TLS-encrypted in motion, but Windows/macOS signing and notarization mitigates any mistakes in TLS implementation (browser plugins aside). And access to a given vault or secret is entirely based on cryptographic primitives. So mostly well and good.

The weakness I saw was that they don't go into a lot of detail on the operational supply and delivery chain for client software -- it may not even be possible to fully guarantee the security of these using cryptographic primitives. One example: an attacker could use a compromised build server to inject an exfiltrator into client software, and we'd be none the wiser.
