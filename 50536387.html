kilburn|root|parent|next|

Vercel UI SDK is a "headless" UI tooklit. "Headless UI" is packaging of behavior that has to be implemented in javascript to get properly working widgets.

For instance, to implement a menu you have to support things like keyboard navigation and auto-closing when the user clicks elsewhere.

Gettings these sort of behaviors right across all browsers is oftentimes _hard_, and testing them properly is very time consuming. That's why it's useful to have it built and tested by a large company.

Traditionally, these behaviors came built-in with your "UI Widget Library" of choice (e.g., https://ant.design/). However, widget libraries bring in their own style and subtle opinions. When you are aligned with those everything is great, but when you want to deviate visually or behaviorally then you have a hard time.

In contrast, "headless UI" packages these behaviors (and only the behaviors) as little snippets that you "plug in" to your own widgets/components. Since how these behaviors get to be "plugged in" to components and how they can interact between them may be dictated by the UI framework/library (e.g., react, astro, solid) the headless ui kits explicitly call those that they support.

For Vercel UI SDK specifically, you can check the list of behaviors they implement here https://ui-sdk.dev/docs/core/behaviors

Tangential, but since the thread is all DOM: I've been using Solid 2's universal renderer for native watchOS UIs, and just put the renderer and host up as an MIT repo: https://github.com/esensible/solid-watch

The bundle (Solid JSX compiled with the new babel plugin) runs in QuickJS-ng on the watch; the renderer emits node mutations over a small host interface; a Swift host lays them out with Yoga and draws with SwiftUI. The same bundle runs in a browser harness for development. The structure is borrowed from React Native's Fabric: three trees, batched commits, one schema that generates the prop code for both sides. A dozen node types, React Native style names, on purpose.

For context, it's the display layer of a larger personal project (not open source at this point): application state lives in a small expression language with a Rust evaluator, running on the phone or on an ESP32 box, with the state, events and view described by JSON Schemas and a schema-derived wire codec. The watch and an e-ink display are synced views of that state. Bundles and firmware are served and updated over BLE, and the phone app has a sign-in-with-ChatGPT authoring mode that writes the Solid UI and the expression logic against those schemas, checks them on the device, and packs the bundle locally on the phone, no server. Solid's universal renderer is what made the watch part feasible: the UI author writes ordinary JSX and the same bundle runs on the wrist and in a browser tab.

Rough edges in the public piece: you build the QuickJS xcframework yourself, and getting a bundle onto a real watch still means an Xcode build. Examples built with plain npm and the browser harness are in the repo if you want to poke at it. Moving from the RCs to 2.0.0, the only breaking change I hit was <Show> compiling to a ternary, which only reordered mutations inside a commit.
