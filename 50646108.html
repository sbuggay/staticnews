Yes, absolutely you can build a web server or CLI tool in Lean.

Lean is a pure functional programming language whose type system is strong enough to write proofs. To keep proofs sound, it adds some constraints, but there are escape hatches and you can absolutely use them for general purpose programming.

> Do “proofs” make sense in the context of regular ol’ software?

Yes! You can write proofs about invariants in your program and have the compiler enforce them. For example, you could write a list index function that requires a proof that the index is in bounds. Writing proofs is hard and you have to think like a type theorist, but you can do some really cool stuff in these languages.

jameshart|prev|next|

Up until the 1920s or so, ‘finding a new chemical element’ was the effort of investigating obscure ores, obtaining samples of peculiar crystals from remote mines, isolating and testing their components, and meticulously demonstrating that the processes used resulted in production of a new substance.

Then in the 1930s it started to become possible to synthesize new elements using cyclotrons and electron and neutron and alpha particle bombardment. Technetium showed up almost as a surprise side effect in some molybdenum that had been in a cyclotron. Pretty soon it wasn’t a matter of ‘how will we find this element?’ But more ‘how will we use these new tools to produce this element, and then be able to tell when we got it?’

Mathematical facts like these might be becoming like elements became in the 1940s: we know that this problem has a complexity; now we have a machine which can tell us what that complexity is. We don’t need to go hunting in mines for where to find it.

Does that change things? Sure, some. Did element synthesis change chemistry? Not drastically. The elements were known to be out there, getting hold of them just gave the ability to confirm expected properties.

These findings - even if we get one like P≠NP - are kind of like that. We are pretty sure they’re out there. And if OpenAI or Anthropic manage to pluck one out of their neural cyclotron it is an impressive achievement - just like when a lab announced ‘we made element 107’ was impressive, but ultimately… not that big of a deal.

jltsiren|root|parent|prev|next|

The external memory model is from the 1980s. You have unlimited external memory and a cache of size M, and you can copy data between them in blocks of size B. Computation is assumed to be free, and you pay a unit cost for each copied block. It's a pretty reasonable model, as long as the cost of computation is negligible relative to I/O.

And that evolved into the cache-oblivious model in the 1990s. The model is essentially the same, except that you don't know the parameters M and B. It's reasonably good at modeling systems with multiple levels of caches, as long as memory access is the actual bottleneck.

You can do the same thing with other operations as well. If you can assume that a certain operation is the bottleneck, you can analyze algorithms by counting those operations and ignoring everything else.

Things become problematic when there is no single bottleneck. You could introduce multiple cost units (such as computation and I/O) and analyze algorithms in terms of them. But then the cost units are incomparable in the general case, and you have to make specific assumptions about the environment to compare the performance of two algorithms.

smaudet|root|parent|next|

Unless I have missed some major hardware developments, current computer architectures are not physically restricted in the fashion that they would need to be to rule out the possibility of inappropriate memory access, as I understand it there are (I'm very much oversimplifying things) two main ways this access is restricted:

1) The operating system designates what memory a process is allowed to access 2) The system itself obfuscates which memory addresses map to which "real" memory areas.

The first depends upon the security of the system (memory is required to remember what memory is allowed to access what memory) - any flaw in that access or method of subverting that access (such as bit flips) provides the possibility that the operating system level security is rendered irrelevant. Unless you can prove that your system is immune, not only logically, but physically, this is a relatively soft guarantee...

The second is essentially a cipher, which provides a stronger guarantee - if you don't know where any of the "real" memory is, accidentally accessing the right memory cell to subvert the memory access controls becomes computationally (time) prohibitive - you can crack a cipher given enough time and energy, but without finding a mathematical shortcut the cost is prohibitive enough that it is not considered possible (the foundational principle of all cryptography).

As I understand it, escaping a sandbox is difficult, mostly because of the hardware level scrambling that is provided, that makes it nearly impossible to affect the memory in control of the memory access (operating system level access). Given some of the mentioned AI attacks involving agents communicating cross-sandbox on the same systems, they clearly are able to leverage e.g. side-channels to effectively communicate despite 1) and 2)...demonstrating at the very least the inadequacy of the current protections, while leaving the door open to better cryptographic measures.

However, if the cryptographic primitives themselves are broken, the no additional amount of cryptographic protection will help here.
