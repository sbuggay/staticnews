As much as I wanted to say you’re wrong, you’re right. After reading TFA, the security boundary is not sound.

Wanting agents to act like you is wrong. You need to own that trust boundary. Build whatever tooling satisfies the contract that agents should have a “not”+<you> (or <you>+”-agent”) identity, and you actuate across that boundary explicitly.

For example, I have a second agent GitHub account that points at my human one. That allows me to write a trusted proxy that ACLs its identity tightly.

It cannot write to public repos ever. In the worst possible case, it externalizes to a private repo’s issue tracker. (Still has never happened in ~4 months)

Once you have this, you can let agents run free. But, it isn’t trivial to set up. Moreover, people don’t want to “do the work.”

All this assumes you abide by “never run untrusted agents on trusted hardware.”

saagarjha|root|parent|next|

What I do on my machine is I basically do not allow for local exec at all, except in some very specific scenarios where I carefully design the environment and make sure that it seems reasonable before handing it to the agent. For example, I have a specific profiling task that requires performance counters. Normally my agents can spin up VMs to run commands without my permission but in this case the counters are not exposed in the VM, which basically means that this must be run outside of the VM. In this case I have configured my setup to be that the agent is allowed to write to a binary at a specific location, and I approve of it running one command (in this case, without my supervision even) that is basically xctrace sandbox-exec [very restrictive handwritten profile] [this binary]. In this way, it can run code on my machine and get the metrics it wants, but it can't go "oh let me write a program to go and poke around the host machine" which it is prone to doing if you don't restrict it this way.

I guess what I have done is the exact opposite in that I have designed an environment for agents and then I am using it as a hammer to solve all my problems, I have had almost exactly the same problem as you and the the way I typically solve it is that I have persistent SSH connections already supported in my harness, and I can arbitrarily expose whatever I want into the "agent environment" (which doesn't necessarily need to even have an agent living there), and this environment is able to connect to the place that doesn't have the credentials, and then I can set up a way for reverse access to work with this tunnel.

blop|prev|next|

fnox (https://fnox.jdx.dev/) is another solution which is also fantastic for day-to-day human use in the cli. It works a bit like sops but can also chain multiple encryption providers, so for example you can use an encrypted age key with a fido2 provider (a yubikey for example) as the main provider of all the secrets on your computer.

If you run for example `fnox exec gh`, fnox will ask you to touch the yubikey to decrypt the age key and decode the github token env var for the gh cli (fnox can also cache the decoded value for a bit, like gpg agent). You can tell the AI agent to use `fnox exec gh` to access gh without seeing the gh token. Or create a shell alias so it's transparent. It also has an MCP server and proxy server to filter API calls to remote APIs (I haven't tried that yet)

it supports quite a few providers (https://fnox.jdx.dev/providers/overview.html): age, fido2, AWS, Azure, Google, kubernetes secrets, vault/openbao, 1password, bitwarden, keepassxc, etc.

A lot of them are read/write so you can also use fnox to sync secrets across different systems.
