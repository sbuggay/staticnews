People here might be interested to know that you can run Scheme (lisp) code directly in Ableton through my Scheme for Max project in Max for Live.

S4M is an open source extension to Max that allows you to run the s7 Scheme interpreter in a Max object, similar to the JS object in Max. Advantages over JS are that in can run in the high priority scheduler thread, enabling accurate timing, it has direct access to the file system from Scheme code, and allows you to make Scheme s-expressions directly in Max messages. It is also a very nice way to control the Live API, as the live API works on lists of symbols.

https://github.com/iainctduncan/scheme-for-max https://www.youtube.com/c/musicwithlisp

I'm planning another major release in the next few months as part of my PhD work.

diskzero|root|parent|next|

I have worked on the code of legacy applications like MasterTracks Pro, Studio Vison and SAW and my opinion would be that you need to start from the ground up with collaboration as the guiding light. The existing applications have workflows and data models that are very monolithic and tied into the concept of a single user, using a single application with application logic and workflows implemented in code. That code sometime exposes functionality through scripting dictionaries or plugin APIs, but the this is backward in my opinion.

Other commenters have stated what a pain it is to just get two environments in sync. A complex production will have tons of plugins, various MIDI and audio interfaces, differing outboard gear and other variables that make life hard when sharing files.

You also have asset management issues; where are the audio stems, vocal tracks, library resources, etc. stored and how are they shared.

If you want to collaborate in real-time, then there is another layer of technical challenges.

I have been working on a system that is influenced from my earlier experience building audio tools for earlier generations of sequencers and DAWs, rendering pipelines for Dreamworks and configuration management systems for Amazon. I feel you really need a system that uses a DSL and all operations are defined at that level. There shouldn't be anything you can do in the user interface that isn't available at the DSL level. You can then think about techniques used in Docker, k8s, etc. to define and deploy both the environment and the interpretation of the DSL in the user interface.

piva00|root|parent|next|

Modulators [0], for example, they are available as a side-panel on any device which you can click the rectangle with a "+" button and select any type of modulator: LFOs (many different kinds), curves, envelopes, segments, etc.

Instead of creating a LFO as part of the chain of devices it's clearly a thing embedded to the device itself, including on VSTs (so any VST can have more complex modulation than they offer natively). You can multi-target the modulator to affect any parameter on any of the devices across the whole track, so a LFO modulating something on the 1st device in the chain can also apply the same modulation to a parameter on the 9th device so they can be "coupled" to that movement, this mapping is also attenuated per application so even though the movement is the same it can have different magnitudes when assigned.

It completely removes the need of LFO Tool for complex curves/ramps, etc., or the LFO as a device with the "map" button to assign to parameters, if I want 10 LFOs I can just have them all together as a side-pane of a device or the track itself. It makes much more sense that a modulator is attached to something instead of being its own thing on a long list of devices.

Another improvement: macros can live on a control panel for a device, whole track, or even the whole project, so you can create a macro knob at the project-level and map it to affect any parameter of any track, and just map the project-level macro knob to a MIDI controller to modulate whatever parameter in the whole project.

These are just a couple of intuitive features from the top of my head I use in almost every single project.

[0] https://www.bitwig.com/userguide/latest/the_unified_modulati...

Quick edit: another feature I remembered after writing this comment that I find more intuitive is the creation of control pages for a device, it's accessible right below the "modulators" button and opens a side-pane to create up to 8 control knobs mapped directly to a device's/VST's parameter or even mapped to a "macro" modulator which itself can be mapped to many parameters of a device/VST, it's really intuitive to create pages of these controls and only use the controls themselves to change parameters, I barely open the VST window after experimenting a bit with which parameters I want to play with and mapping those to controls.
