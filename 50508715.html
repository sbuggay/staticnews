spacechild1|root|parent|next|

`string_view` (and `std::span`) is great! Finally I don't have to use concrete types like `const std::string&` or `const std::vector<float>&` as function parameters when all I really want is just something that behaves like a string or array/vector type.

In fact, `std::string_view` can lead to very elegant and efficient (zero-allocation) string parsing code.

IME, taking a string_view as an argument is pretty unproblematic. Two areas where I have seen problems:

1. returning a string_view from a function. Think twice before doing that.

2. calling data() and passing the result to a function that expects a null-terminated C strings. (std::string_view is not guaranteed to be null-terminated.)

---

Apart from that, there are so many great features and libraries in C++17 and C++20 that I use on a regular basis and that I would really miss:

- structured bindings

- if-statement initializers

- fold expressions

- inline variables (very useful for handling global state in header-only stuff)

- if constexpr (replaces many uses of SFINAE)

- concepts (replaces all of the remaining uses of SFINAE)

- coroutines (really nice to use with ASIO)

- std::optional

- std::variant

- std::filesystem

- std::format (although I personally stick to fmt::format)

- from_chars() and to_chars() (fast, local-independent string-number conversion routines)

- std::bit

- std::apply, std::invoke, std::bind_front

- etc.

> What does behave like a std::string/std::vector but is not std::string/std::vector, respectively?

`std::span` works with all vector/array-like types: `std::vector`, `std::array`, C-arrays and third-party vector/array types.

Similarly, `std::string_view` works with `std::string`, C-strings and third-party string types.

> so that the autovectorization can kick in

It's not even about vectorization. Often you just have a function that takes a string-like or array-like thing, but you don't care about the exact container. Yes, you could make the argument a template (and constrain it with concepts), but then you have to put everything in headers.

jandrewrogers|parent|prev|next|

In the case of C++, "modern" conventionally denotes "C++11 or later". Idiomatic code between "legacy" and "modern" dialects of C++ that they almost look like different languages. C++11 was a breaking change to the idioms of older C++.

This is helpful context to the reader. Many C++ programmers are unfamiliar with either idiomatic legacy or modern dialects and would have difficulty following the code.

There are arguably three different idiomatic dialects of C++ now: legacy, C++11, and C++20. We don't really have a common term for distinguishing between C++11 and C++20 even though the idiomatic code looks quite different.

It has been an interesting evolutionary strategy. C++ standards meticulously avoid breaking changes but will happily do a major redesign of how idiomatic code is written.
