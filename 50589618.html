alethic|root|parent|next|

This is just a performance issue. In theory, the Lean kernel could be written in Lean.

These independent kernels do not prove their own consistency -- rather, their function is to act as slower but more idiomatic/simpler implementations of Lean's meta-theory. It doesn't matter that they don't correspond 1:1 with Lean's official kernel at either a theoretical or an implementation level, because the independent kernels are not for proving Lean correct -- they're for auditing complex proofs, in a simpler system.

What is particularly interesting is that then these independent kernels are "proven correct"! This notion of correctness is specifically that con-leche (et al) will only accept theorems that are also correct with regards to a particular model of set theory, with membership / extensionality / other standard ZF axioms, and an infinite hierarchy of universes. This is (vaguely speaking) a set-theoretic model of Lean. It is here that Gödel's incompleteness theorems come into play. Lean indeed cannot verify that this set-theoretic model is "correct": what it can verify, however, is that the type-theoretic machinery is correct with respect to the set-theoretic machinery. This removes the possibility of an invalid proof slipping by by way Lean's comparator (which can run alternative kernels) by way of an implementation bug.

It leaves the possibility that Lean's metatheory is inconsistent. This is quite unlikely. The foundations of mathematics have been well-studied, and Lean builds directly on the huge amount of work that has been done, particularly by the Coq community, in figuring out what is and isn't consistent. The Coq theorem prover was really developed in conjunction with modern type theory... Lean came in after a lot of meta-theoretic issues had been ironed out, thanks to them.

I am sure you will get some more detailed answers; I am a bit lazy today; so I will give you the very high level / informal version of the answer (Edit from the future: It grew longer than expected, whelp :D):

Gödel's two incompleteness theorems basically amount to "As soon as your system can do a ridicolously little amount of things, then either of two things is true in this system: 1) You can express facts in your system that you cannot prove within your system or 2) your system claims that some false statement is true."

Now, because 2) is way way worse than 1), you design your systems so that you are firmly in the 1) camp - that way, we gain full confidence in the results our systems proofs, and the price we pay is that our system is less powerfull than it could be.

With Lean, it's similar. The foundation of Lean comes from type theory. There, we do something that is familar to above: We restrict our power (i.e. "which Lean statements do get verified by lean?", and we gain absolute confidence in its proofs (ignoring implementation errors, hardware limitations etc. for now). Intuitively: We have to work harder to satisfy the typechecker/prover, but when it is satisfied, then we have confidence in it.

-------------- Deeper down the rabbit hole

You might have noticed that I seem to muddle the waters a bit with programs, proofs, types and so on... There is a deep reason behind it! In a very strong sense, programs = types = proofs... So, here is how it is all connected (including the RH):

- Lean is a programming language (like Haskell, Rust, ... There is nothing stopping you from writing a server in Lean and deploying that binary somewhere in the cloud. Regarding developer experience, you could think of it like a modern Haskell without lazy evaluation and without its historical warts)

- programs can be tied to types: We first check if the whole program as such has a type ("do all of its parts fit together in a strictly defined way?"). Only if it does, we proceed (and for example, run it). If it does not, then the compiler declares "this program is not good! here is a type error!". Now, here is the price hat Gödel proved we cannot avoid (if we want to trust the typechecker): There are programs that don't type check, but behave perfectly fine at runtime. (That's the "we limit our power" part - those are perfectly good programs where the compiler throws their hand in the air and gives up!)

- Enter the third puzzle piece: proofs and the Riemann Hypothesis: turns out, we can think of types as theorems, and a successful type check as a correct proof! And the RH is a hypothesis we would like to prove...

- So here is how it all ties together: RH is written so that it can be used as a type, in the Lean programming language. The "main program" is basically just another ordinary function with some input types, and returns the type version of the RH being true. Because the function needs an implementation, we are forced to implement that function body - which are many small functions that correspond to mathematical theorems/lemmas if you look at it with the proof glasses on. From the programming pov, it is just functions that call functions that call functions and so on. And from the typechecking point of view; we compose a bunch of functions and check whether input types and output types match up.

Finally, the payoff: *If that program typechecks, then we know RH is true*, which is what just happened!

(PS: The same principle is behind the computational proof of the four-color-theorem. The proof of the four color theorem is "simply" a program that typechecks, where the final type happens to correspond to "can we color any planar graph with at most 4 colors?")

alethic|root|parent|next|

This is a very good question! There are two answers.

First off, you can absolutely do what you are describing. There are systems like Metamath that assume nothing beyond first-order logic and the axioms of set theory, and apply these verbose rewrites. See https://en.wikipedia.org/wiki/Metamath for more. However, Lean (and many past theorem provers, too) have 1) preferred to represent mathematical objects as types rather than sets, and 2) built a large amount of interactive tooling rather than the blind rewriting of Metamath. The first choice is essentially of elegance -- the Curry-Howard correspondence indeed lets you write propositions as types and proofs as terms inhabiting those types, which is a connection of deep beauty. Ontologically, there is also an argument to be made that representing a mathematical object as a type is more "correct". We don't really think of ex. two as "{{},{{}}}" or "{{{}}}". We think of it as "Two", or maybe "Zero +1 +1". This is a win for types. Mathematical objects are not grocery bags.

Second, the historical approach to theorem proving has been interactive theorem proving. Theorem provers were supposed to be a second brain for students and computer scientists and mathematicians... keeping track of assumptions, suggesting possible tactics to take... aiding the human in the process of proof (and subsequently understanding), rather than replacing them. The path of uncritical adoption of AI that Lean has taken, sadly, much replaces the human. There is no real pragmatic reason for Lean to retain its interactive (human) elements any more (besides inertia) as AI scales up. It might as well be Metamath, indeed.

It’s the nature of mathematical ideas and methods that they are reducible to their component parts, so if you really want to, you can nearly always claim that something is just recombining existing knowledge. Motivated reasoning, from people dead-set on embellishing or downplaying a result, is hard to avoid here, so all you can really do is make an earnest and sincere judgment call based on the fine details of the mathematics.

For example, it is my opinion that the Jacobian conjecture counterexample was, in retrospect, easy and classical and hiding in plain sight, and that it’s a bit embarrassing we didn't find it decades ago. In contrast, the Unit Distance Conjecture counterexample seemed to me to use a stroke of genius by applying techniques from class field theory to approach what seemed like a problem in discrete geometry and combinatorics. It’s a neat, if annoying, feature of math that once we find a long-sought solution to an open problem, we reserve the right to retrospectively change our mind about the value of the problem if the solution turns out too easy or uninteresting. We just have to try to be fair and honest about it (the word “just” is doing some heavy lifting in this sentence).

Anyway, I don’t think “brute force recombination” is likely to be meaningfully the case here with GRH, though we won’t know for sure until the proof has been simplified and distilled. gregdeon|parent|next|

The proof is written in a programming language called Lean. Very roughly, Lean is set up so that proofs are functions and theorems are types in this language. Verifying that the proof is correct essentially amounts to compiling the program and confirming that it doesn't have any type errors. Several people have compiled the program successfully, so we believe it's correct.

The biggest concern that people have is that there might be a bug in the type checker that the proof is exploiting. But a) it's been compiled with multiple independently-implemented compilers, which are are unlikely to have the same bugs, and b) some of those compilers have themselves been proven to contain no bugs. So, it is exceedingly likely that the proof is legitimate.

Now, whether we can understand the proof is an open question...

There are still a few ways that the proof might be incorrect. Of these, the most likely is that the proof was generated by a misaligned AI system that found and intentionally exploited a lean bug in order to fool its human evaluators (i.e. shades of the HuggingFace attack). I personally don't think this is very likely, but you'd have to understand a bit more about the agent systems used in generating the proof to come up with a more informed estimate.

Another possibility is that an aligned system came up with a plausible but incorrect idea along the way, and simultaneously stumbled across a lean bug that led to an incorrect verification of this idea. I'd put the likelihood here as vanishingly small due to the requirement of serendipitous factors, but it's nonzero.

You could also ask whether an aligned AI system could "p-hack" its way into finding a serendipitous lean bug by trying a large number of approaches. I think this is also vanishingly unlikely because the AI system is trained on and therefore "thinking in" natural language, and presumably only translating results into lean after it believes them to be correct.

And of course there's the possibility that the lean proof isn't faithful to the natural language description we've been given, but that is ruled out in this case due to the use of the canonical problem statement in mathlib. Otherwise, this would certainly seem like the most likely way the proof could be incorrect.
