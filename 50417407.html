jcbrand|prev|next|

I'm exploring using XMPP as a coordination layer for multiple LLM agents.

I'm using Herdr to run multiple agents in parallel, and my goal is to see whether I can get them to collaborate more efficiently.

For example, when one agent's PR gets merged, other agents immediately become aware of it, rebase their own PRs and fix conflicts.

What also often happens is that new tangential requirements and sidequests often arise while working in a session, and I now let agents hand these off to parallel Herdr tabs. The handoff can be done with or without XMPP. These parallel agents announce their statuses in the XMPP MUC (groupchat), which enables them to coordinate.

Technical details:

Converse XMPP client runs as a headless NodeJS daemon with a CLI that can be called by agents.

I created a /coordination skill which is enabled by default via a Claude Code hook. When an agent starts, it ensures the Converse daemon is running and then joins a password-restricted and members-only MUC where all the other agents in that Herdr workspace are as well (and also myself). I can then assign that agent tasks via messages in XMPP (DMs or groupchat) or from Claude Code.

Once the agent has the task, it announces it in the MUC so that other agents are made aware. When sidequests or requirements arise in that session, it can ask in the MUC whether other agents are idle and able to take over that parallel task.

I've been building the Converse daemon and CLI and have now been experimenting with the workflow and working out various kinks and use-cases.

There are various other XMPP features that can be explored further. I'm thinking of using PubSub with a web UI with vertical swimlanes which can show me which agents are currently active, what they're working on and for how long.

I'm using Claude Code because that's what we use at $WORK, but this should be independent of any harness and part of the point is create neutral tools not locked into any particular inference provider.

Joel_Mckay|parent|prev|next|

Did something similar years ago, and most opto-couplers only have a switching response time around 100kHZ at best.

High precision instrumentation just uses a stable comparator to sync the AC line Zero crossing events, and times the sharp roll-off gap over several cycles to estimate the center transition event. This allows readings to be synced in the low-noise state of the power lines cycles, and time what the readings should be when monitoring the voltage, temperature, and current across the cycles.

Additionally, most >8-digit meters internal power supply will have a tuned filter for the 60Hz/50Hz line. Getting a line filter will often give a digit of precision on older equipment, and clip-on line chokes in bulk also help.

https://www.digikey.com/en/products/detail/eaton-tripp-lite/...

One final tip, anything beyond 12bits precision or 60MHz wide RF bandwidth for SDR will almost certainly have an export restriction. Wideband devices also have RF front end saturation issues, and usually require narrow band-pass filters to see the hydrogen line etc. Best of luck =3

Ur is an (very in-progress) universal formatter and linter for every programming language. It's in preview right now, which just means friends are messing around with it and having a good time pointing out all the bugs. Docs are mostly up to date, but buyer beware. Implementation wise, it's the Rascal meta language reimagined in Rust with some features from JastAdd thrown in there for good measure. Ur is incremental/persistent between runs, it's built on top of Mambo, a library that drops in as a replacement for Salsa and persists all queries to disk automatically.

https://ur.dev/en/

Ur has some pretty good static analysis and code rewriting tools hidden inside of it that'll get documented later on. These tools have been developed in tandem with a static mass rewrite of some core parts of the Rust compiler. It's very much not done, but it's made pretty good progress towards putting all crates in one process, dropping memory after a crate is done compiling, and full incremental support across all commands. Here is a literate program that explains why, how and which changes are being made (I haven't read all of it myself yet, lots still changing). Aiming to have this out by end of the month.

https://breakneck.powderworks.dev/
